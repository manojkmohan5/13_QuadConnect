# QuadConnect Staff and Developer Guide

## 1. About this guide

This guide is for the people who run QuadConnect rather than use it: the staff who review venue suggestions and look after the data, and the developers who install, test and deploy the app. Students have their own handbook, which explains the same app from their side. QuadConnect is a Django web application. Its code is one Django app called connect, its settings are in the quadconnect package, and its page templates are in connect/templates, with the sign-in pages in the top-level templates folder. The stylesheet, the Inter font and the Vega libraries for the charts are in the static folder. Most of a reviewer's daily work happens in the admin site, which has its own section below.

QuadConnect has two kinds of user. Students sign in and use the pages that the handbook describes. Staff are Django users with staff status: they see the same pages, and they can also open the admin site at /admin/. A few student pages behave differently for staff. The Campus locations page lists the venue suggestions that are waiting for review, and the page of a venue that is not approved yet, which students cannot open, opens normally for staff. The admin site has no login page of its own. It sends people to the same allauth login as the rest of the site, so staff sign in once for both.

The data in the prototype is sample data, loaded by the command python manage.py seed_demo_data. It creates 28 interests, 4 venues, 8 student profiles from 6 colleges, 41 interest choices, 16 free slots, 19 matches over nine weeks with 55 participants, and 33 feedback entries, as well as two superuser accounts for the course staff. The seeded students have unusable passwords, because students are meant to sign in through the university's single sign-on, which the prototype does not have yet. The command is idempotent and deterministic, so running it twice changes nothing, and it runs as one database transaction, so a failure leaves nothing half loaded.

## 2. Running QuadConnect on your computer

QuadConnect needs Python 3.11 or newer, and the automatic checks on GitHub and the live site both use Python 3.12. Create a virtual environment in the repository folder and install the packages with pip install -r requirements.txt. The file pins 61 packages to exact versions, among them Django 5.2.17, django-allauth 65.19.7 for sign-in, WhiteNoise for static files, Matplotlib and vl-convert for the charts, and torch and transformers for the local language model. On Linux, adding the option --extra-index-url https://download.pytorch.org/whl/cpu installs the CPU-only build of torch, which is enough for QuadConnect.

Every secret, and every setting that differs between machines, comes from a file called .env in the repository folder, which is never committed. Copy .env.example to .env and fill it in. DJANGO_SECRET_KEY is the one value that must be set before anything runs: without it, Django stops at start-up with a message asking you to copy .env.example to .env and fill it in. Generate a new random key for each machine rather than reusing one. The other keys are optional on a development machine: the Google client ID and secret, the venue-check provider and its API key, the switches for the local language model, and DJANGO_DB_PATH, which points the app at a database file outside the repository.

With the environment ready, three commands give you a working site. The command python manage.py migrate creates the tables, python manage.py seed_demo_data loads the sample data, and python manage.py runserver starts the development server. The repository already contains a db.sqlite3 file with the seed data in it, so the first two commands matter only for a fresh database. To start again from scratch, delete db.sqlite3 and run them both. The first start can pause for up to a minute on Windows while Matplotlib builds its font cache. This happens only once, and later starts are quick.

The command line uses the development settings, quadconnect.settings.development, unless the environment variable DJANGO_SETTINGS_MODULE names others. They turn DEBUG on, accept only localhost, 127.0.0.1, [::1] and Django's test server as host names, and print any email Django would send to the console instead of sending it. More host names can be added with DJANGO_ALLOWED_HOSTS. Everything else comes from the shared base settings: a SQLite database, the America/Chicago time zone, WhiteNoise for static files, and the middleware that requires a login on almost every page. To try the production settings locally, set DJANGO_SETTINGS_MODULE to quadconnect.settings.production and fill in the keys they require.

## 3. Production settings and security

The web server uses the production settings, because wsgi.py and asgi.py both point at quadconnect.settings.production. These settings turn DEBUG off, and they refuse to start without DJANGO_ALLOWED_HOSTS or without a Google client ID. Static files are served by WhiteNoise from compressed copies whose names include a hash of their content, which is why collectstatic must run before the site starts: without it, every page that uses a static file fails. Email goes to a dummy backend that discards every message, and the site writes its log to the console at the INFO level.

Some protections are always on in production. Browsers are told not to guess content types, the referrer is sent only on requests within the site, no other site may show QuadConnect inside a frame, and scripts cannot read the session cookie. Setting DJANGO_SECURE_SSL to 1 adds the protections that need HTTPS. Plain HTTP requests are redirected to HTTPS, the session and CSRF cookies travel only over HTTPS, HSTS tells browsers to use HTTPS for a year, including subdomains, and marks the site as ready for the browsers' preload list, and allauth builds its links with https. Turn it on only once the site is really served over HTTPS, because browsers remember HSTS.

Continue with Google is the only sign-in through another service. It asks Google for the profile and email scopes, uses PKCE, asks for online access only, and makes Google show its account chooser every time. Without GOOGLE_CLIENT_ID, the button is simply not shown on a development machine, and once the ID is set, the secret must be set as well. The Google client comes from the environment, never from the database. A Google sign-in never opens an existing account just because the email addresses match: the addresses on QuadConnect are never verified, so whoever registered an address first would otherwise receive its owner's Google sign-in.

Students and staff log in with a username or an email address and a password, and the sign-up form asks for a username, an email address and the password twice. Email addresses are not verified, and the login form leaves out the usual link for a forgotten password, because the app sends no email. Failed logins are rate limited by allauth, and further attempts on an account are refused after five failed logins in five minutes. The limits per visitor use the visitor's real IP address, which QuadConnect's account adapter reads from the X-Real-IP header when the hosting proxy provides it.

## 4. The admin site

The admin site at /admin/ is where staff change data directly. All eight of QuadConnect's models are registered there: student profiles, interests, profile interests, availability slots, campus locations, matches, match participants and experience feedback. Its pages carry the title QuadConnect Administration. There are no custom actions, so apart from Django's built-in action for deleting selected rows, staff change records one at a time. The one exception is the approval box on the list of campus locations, which can be ticked for several venues and saved in one go.

The list of student profiles shows each student's name, NetID, college, preferred connection, social energy and whether the student is SSO verified. It can be filtered by connection type, conversation style, group preference, verification and college, and searched by name, NetID, Illinois email address or department. A profile's page also lists the student's interests and free slots, so a reviewer can correct them without leaving it, and it shows when the profile was created without letting anyone change that date. Unticking SSO verified takes a student out of the weekly matching pool without deleting anything.

The list of interests shows each interest's name, its category, whether it is active and how many times students have selected it, and it can be filtered by category and by status. The categories are hobby, registered student organization and meeting activity. An interest that a student has picked cannot be deleted, because the database protects it. Untick its active box instead, which retires the interest while keeping every student's history. The same name may appear in two categories, as Food does among the hobbies and the meeting activities, but never twice in one category.

The list of campus locations shows each venue's name, street address, whether it is indoors, its seats, whether it is approved, the automatic check's verdict and how many matches it has hosted, and it can be filtered by indoor, approved and verdict. The check's verdict, flags, reason, model and time are read-only, so a reviewer can read the advice but never edit it. The list of matches shows each match's check-in code, connection type, week, date, venue, status and number of participants, with links at the top to narrow the list by date. On a match's page, its participants can be added or removed, and their check-in times are read-only.

The list of match participants shows each student's match, response, fit score and check-in time, and it can be filtered by response, connection type and week. A participant's page also shows the feedback that the participant left, if any. The list of experience feedback shows each review's participant, rating, stay-connected answer and submission time, and it can be filtered by rating, by whether the student wants to stay connected and by whether they felt comfortable. Staff can read the private notes in the admin site. The notes are never shown to the other students in a match, and the match page does not load feedback at all.

## 5. Reviewing venue suggestions

When a student sends a venue suggestion from the Campus locations page, the view saves it with is_approved set to False, although the model's default is True, and the form has no approval field at all. The student then sees a message saying that the venue was sent for review and will be listed once staff approve it. Until then, the venue is left out of the venue list and the API, and its page returns a 404 for everyone who is not staff, so that the page does not even reveal that the venue exists.

Staff see each waiting suggestion on the Campus locations page, under the heading Waiting for review (visible to staff only). Each one shows the venue's name and street address, the automatic check's verdict, or not run when there is none, the check's flags and its reason, and a Not approved badge. Below the list, a link opens the admin list of campus locations filtered to the venues that are not approved. To approve one, tick Is approved for it there and save. Judge the venue yourself, using the check only as advice: it should be a public, staffed place on or near campus, with a complete street address and an arrival note that says where to wait.

When the automatic check returned a verdict, the student who sent the suggestion also sees it, in the form Automatic check, then the verdict and the reason, followed by the sentence Staff make the final decision. When the check did not run, the student sees only the message about the review. A suggestion with a problem is not saved at all. The form refuses a venue that is already listed or already waiting, a missing name or street address, and a number of seats outside 2 to 50, and it shows the problem next to the field concerned. A double click cannot save the same venue twice, because venue names are unique.

Each user can trigger at most five automatic checks an hour. A suggestion sent after that is still saved and waits for review, but without a check, and staff see its verdict as not run. Before anything is sent, the text is cleaned and checked for instructions aimed at the AI, and both steps add flags of their own. A suggestion that contains an email address, a phone number or a link is therefore flagged for contact details, and one that tries to give the AI instructions is flagged as a manipulation attempt, even when the AI service cannot be reached. When the service does answer, a manipulation attempt always turns its verdict into likely unsuitable.

## 6. How the automatic venue check works

The automatic check is in connect/ai_venues.py. By default it calls Groq's chat completions API with the model openai/gpt-oss-120b, at temperature 0, with at most 600 tokens and low reasoning effort, and it gives up after 10 seconds. AI_API_PROVIDER can name another provider. The code also knows OpenRouter, which uses the same model, Gemini, which uses gemini-2.5-flash, and Hugging Face, which uses Qwen2.5-72B-Instruct, and AI_API_MODEL can override the model. The key comes from AI_API_KEY or, when that is empty, from the provider's own variable, such as GROQ_API_KEY. With no key, nothing is sent.

Only the venue is sent: its name, street address and arrival note, each cleaned and cut to 200 characters, together with whether it is indoors and how many seats it has. The student who suggested it is never included, neither their name nor their username nor their email address. Cleaning first normalises the text and removes invisible characters. It then replaces email addresses with [email], web addresses and links with [link], and phone numbers with [phone], and any replacement adds the contact details flag. A separate check looks for instructions aimed at the AI, such as ignore the previous instructions or you are now, and adds the manipulation attempt flag.

The service must reply with a JSON object holding a decision, a list of flags and a reason. The decision is approve, review or reject, which people see as Looks suitable, Needs a closer look and Likely unsuitable. The eight flags are private residence, isolated or unsafe, alcohol or nightlife, far from campus, unclear details, advertising or spam, contact details and manipulation attempt. The code then applies rules that can only make the advice stricter, never looser: a manipulation attempt always becomes reject, and contact details or any of the four serious flags turn approve into review.

The result is stored on the venue in five fields: the decision, the flags as a comma-separated list, the reason, the service and model that checked it, and the time. Only the first 4,000 characters of a reply are read, unknown flags are dropped, and the reason is cut to 249 characters. If anything goes wrong, whether a missing key, a timeout, an HTTP error, a rate limit at the service or an unreadable reply, the decision stays empty, the flags found by the cleaning step are kept, and the reason starts with Not checked automatically. The check never raises an error into the page, and it never touches the approval field, which only staff change.

## 7. Ask in plain English, behind the scenes

Ask in plain English, at /search/ask/, turns a student's request into search filters with a small language model that runs on QuadConnect's own server. The model is Qwen/Qwen2.5-1.5B-Instruct unless AI_LOCAL_MODEL names another one. It is loaded the first time someone uses the page, in float32 on a CPU or bfloat16 on a GPU, and its weights are kept in the Hugging Face cache in the user's home folder, never in the repository. To download the model ahead of time, run python manage.py download_ai_model, which runs one sample search and prints The local model is ready when it works. Setting AI_LOCAL_ENABLED to 0 switches the model off.

The model may choose only from six filters: up to four interests, a college, a connection type, a weekend day, one of the four time windows, and an energy level of quiet, balanced or social, which stand for social energy 1 to 2, 3, and 4 to 5. Its prompt lists the active hobbies, student organizations and colleges from the database and gives eight worked examples. Whatever the model returns is checked against an allow-list. Unknown keys are dropped, and a value is kept only if it matches a real interest or college, ignoring case, by a unique whole word or by a close spelling. The model never sees a student record.

A request must be 3 to 200 characters long, and it is cleaned before the model sees it. Each user may run ten AI searches a minute, and after that the page says there have been too many in the last minute. The model's answers are cached for an hour, keyed by the model, the request and the current interests and colleges. If the model is switched off, is busy with another search for more than five seconds, returns no readable JSON twice, or fails in any other way, the keyword parser answers instead. After a failed load, the app waits five minutes before it tries to load the model again, and a search never ends in an error page.

A request that looks like instructions to the AI, such as forget your rules, reveal the system prompt or you are now, is caught by a pattern and logged, but it is still searched, because the model can only fill in filters. The page then tells the student that those instructions were ignored. On the live site the model is not used at all: torch and transformers do not fit within the 512 MB of PythonAnywhere's free plan, so the live search always uses the keyword parser. The tests never load a model or call an API, and the automatic checks on GitHub run with AI_LOCAL_ENABLED set to 0.

## 8. Icebreakers and the Open Trivia Database

The Icebreakers page of each match, and the endpoint /api/icebreakers/, which takes the match number as its match parameter, fetch trivia questions from the Open Trivia Database at opentdb.com. Each request asks for five easy multiple-choice questions and waits at most five seconds, and no API key is needed. Members who declined the match are left out when the page works out what the group has in common. The endpoint's reply names the questions' licence, CC BY-SA 4.0, and describes the group only by counts, never by names. Nothing from the Open Trivia Database is saved in QuadConnect's database.

Shared interests are mapped to trivia categories. Art and Photography map to Art, Basketball and Fitness to Sports, Gaming and UIUC Esports to Video Games, Movies to Film, and Music to Music. Outdoors and the UIUC Pre-Med Society map to Science and Nature, Reading to Books, Technology and Illini Robotics to Computers, Travel to Geography, and Illinois Student Government to Politics. The page picks the category that covers the most members of the group, provided at least two members share it, and it breaks ties at random. When no category reaches two members, it asks for General Knowledge questions instead.

Questions are cached for only five seconds, so reloading the page soon brings new ones, and a failed request is never cached. The endpoint turns errors into clear status codes: a missing or malformed match number gives 400 and an unknown one 404, a timeout gives 504, a rate limit at the Open Trivia Database gives 503 with Retry-After set to five seconds, and any other failure gives 502. The page itself still shows the group's shared interests when the questions cannot be loaded. The live site can reach opentdb.com because it is on the free plan's allowlist of outside sites.

## 9. The data model and its rules

QuadConnect keeps its data in eight models. A StudentProfile belongs to one Django user and holds the NetID, the Illinois email address, the college and department, and the matching preferences. Interest is the shared list of options, and ProfileInterest links a profile to each interest it picked, with a flag for the starred ones. AvailabilitySlot is one free weekend window of a profile. CampusLocation is a venue, and Match is one planned meetup at a venue. MatchParticipant links a student to a match, with the student's response, fit score and check-in time, and ExperienceFeedback holds one participant's review of the meetup.

Five unique constraints keep the data consistent. A NetID and its Illinois email address form a unique pair, and each one is also unique on its own. An interest's name is unique within its category, a profile can pick an interest only once, and a profile can mark a given day and time window only once. A student can take part in a match only once, and because feedback is linked one-to-one to a participant, each participant can leave one review. Ranges are checked by field validators rather than by the database: a venue seats 2 to 50, a rating is 1 to 5, and a fit score lies between 0 and 100, with two decimal places.

Deletion rules protect history. An interest that a student picked, a venue that has hosted a match, and a student who takes part in a match cannot be deleted, because those rows are protected and the database refuses. Deleting a match deletes its participants and their feedback with it, and deleting a Django user deletes that user's student profile. If a meeting activity that a match suggested is deleted, the match stays and simply loses its suggested activity. To take an option out of use without losing history, retire it instead: interests have an active switch for exactly this purpose.

The command python manage.py verify_constraints proves these rules on the real database. It needs the seed data and runs eleven checks, each inside a transaction that is rolled back, so nothing changes: five duplicate inserts that must be refused, three protected deletions, two cascades and one SET_NULL. It stops with an error if any check fails. The stored values behind the menus are fixed lists. The connection type is FRIEND or SQUAD, the weekday is 6 for Saturday and 7 for Sunday, the time window is 10-12, 12-14, 14-16 or 16-18, a match is PROPOSED, CONFIRMED, COMPLETED or CANCELLED, and a response is PENDING, ACCEPTED or DECLINED.

## 10. Reports, exports, charts and the API

The Reports page counts students per college, split into Friend Connect and Squad Connect, and matches per venue, split into completed and upcoming, where upcoming means proposed or confirmed. It also gives site totals, including cancelled matches and the number of participants. The page links to the two downloads of the student list, at /export/students.csv and /export/students.json. Both have the same twelve columns: NetID, full name, college, department, preferred connection, social energy, conversation style, group preference, interests, number of matches, SSO verification and the date the student joined. The email address is never exported.

The CSV export starts with a byte order mark for spreadsheet programs, joins lists such as interests with semicolons, and puts an apostrophe in front of any cell that starts with =, +, -, @, a tab or a carriage return, so that a spreadsheet cannot run it as a formula. The JSON export holds the time it was generated, the number of records and the list of students. Both file names carry the date and time of the download, in the form students_YYYY-MM-DD_HH-MM, and both list the students sorted by name.

The API page at /api/ documents the endpoints. The endpoint /api/locations/ returns the approved venues as JSON and can be filtered to indoor or outdoor venues and by a minimum number of seats, and /api/locations.txt returns the same list as plain text. The endpoint /api/matches/ lists matches and can be filtered by week, type and status. It shows the participants only as a count, and it leaves out the check-in code. The endpoint /api/summary/ counts verified students per interest, and /api/summary/matches-per-week/ counts the matches and participants of each week, with a zero for empty weeks between matches.

Only /api/summary/ is public, and any website may read it, because it holds counts and no personal data. Every other endpoint answers a signed-out request with status 401 and the message Log in to use this endpoint. Bad query parameters get a 400 reply that names each field and how to fix it. QuadConnect also draws charts: two Matplotlib images, one of verified students per college by preferred connection and one of interest selections by category, each 1200 by 675 pixels with a hatch pattern as well as a colour for every series. Two Vega-Lite charts are built from the summary endpoints, and the server can also render them as PNG or JPG images.

## 11. Tests, automatic checks and deployment

The test suite has 173 tests in four files: 45 in connect/tests.py, 42 in tests_a4.py, 25 in tests_a5.py and 61 in tests_a6.py. Run them with python manage.py test connect. The tests never load a language model and never call an outside AI service, and the venue form's tests run with no API key. Before pushing, also run ruff check . from the repository folder. Its settings file, ruff.toml, selects the pycodestyle errors, pyflakes, import order, bugbear, implicit string concatenation, Django and security rules, with a few exceptions for the notebooks and the test fixtures.

Every push to the branch named in .github/workflows/deploy.yml starts the automatic checks on GitHub: one job, called test, on Ubuntu with Python 3.12 and a limit of 20 minutes. It installs the requirements with the CPU build of torch and checks that the web app's packages stay under 400 MB. It then runs ruff, Django's system checks, a check that no migration is missing, and checks of the committed database: it must be fully migrated and must hold no sessions, admin history, unapproved venues, stored Google client, Google accounts, email addresses or extra password hashes. Then it runs verify_constraints and the whole test suite.

After the tests, the workflow checks the production settings with check --deploy and HTTPS switched on, and runs collectstatic. It then starts the production build and tests it from outside. It requests 18 addresses signed out, expecting the public pages to load and every other page to send the visitor to the login, then 34 addresses signed in, and it checks the hashed scripts and a long-lived cache header on the stylesheet. The workflow is called Deploy, but it deploys nothing. There is no automatic deployment, and the live site is updated by hand.

The live site runs on PythonAnywhere's free plan, in a virtual environment with Python 3.12. Its WSGI file loads quadconnect.settings.production, the address /static/ is mapped to the repository's staticfiles folder, and HTTPS is forced. The live database is kept outside the repository and found through DJANGO_DB_PATH, so pulling new code never touches the real accounts. To update the site, open a Bash console, run git pull, activate the virtual environment, install the requirements if they changed, export the production settings module, run migrate if there is a new migration, run collectstatic, and press Reload on the Web tab.

A free web app on PythonAnywhere has to be extended on the Web tab once a month. The free plan allows requests only to outside sites on its allowlist. QuadConnect needs opentdb.com for icebreakers and Google's googleapis.com addresses for Google sign-in, and both are on it. Each web worker uses about 90 MB of memory, and about 170 MB after it has drawn chart images. A new deployment needs a fresh DJANGO_SECRET_KEY, the production settings module, DJANGO_ALLOWED_HOSTS, the Google keys, and DJANGO_SECURE_SSL set to 1 once the site is on HTTPS, followed by collectstatic and check --deploy.
