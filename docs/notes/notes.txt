--------------------------------------------------------------------------------
S1 - For which feature is get_absolute_url() useful?
--------------------------------------------------------------------------------
  Any feature that links to one record from more than one place. For us that
  is the match. A match is linked from the match list, the home page's
  recent matches, every student's match history, every venue page, and the
  "url" field of the JSON API. All five call match.get_absolute_url(), so
  the /matches/<pk>/ pattern is written exactly once, in urls.py. If the URL
  changes later (say to /week/<date>/match/<pk>/), that is a one-line edit
  instead of five template edits, and a link can never drift out of step.

  It pays off in three more places:
    - Django Admin shows a "View on site" button on every model that has it.
    - The API turns it into a full link with
      request.build_absolute_uri(obj.get_absolute_url()).
    - Templates read as intent: {{ student.get_absolute_url }} says "link to
      this student", where {% url 'connect:student-detail' student.pk %}
      says how to build the path.
  Student profiles and venues use it the same way. Feedback deliberately has
  no detail page and no get_absolute_url(): it is private.

--------------------------------------------------------------------------------
S2 - Why the roster search is GET and the NetID lookup is POST
--------------------------------------------------------------------------------
  GET: results should load the same from the same link. /search/?q=gaming
  can be bookmarked, shared with a teammate, reloaded and reached with the
  back button, and it changes nothing on the server.
  POST: the data should stay hidden. A NetID identifies one person. In a GET
  URL it would land in browser history, the server's access log, any proxy
  log, and the Referer header sent to the next site the user clicks through
  to. In a POST body it goes to none of those. {% csrf_token %} protects the
  form. The page renders straight from the POST instead of redirecting,
  because a redirect would have to put the NetID back into a URL.

--------------------------------------------------------------------------------
S3 - Static file organisation
--------------------------------------------------------------------------------
  One project-level static/ directory (STATICFILES_DIRS), split by type:
      static/css/quadconnect.css     the whole design
      static/img/logo.svg            header logo and favicon
      static/fonts/                  Inter woff2 + its SIL OFL licence
  Project-level, not connect/static/connect/, because the only consumer is
  base.html, which is site-wide; the connect app has no assets of its own.
  If an app ever does, they go in <app>/static/<app>/ so two apps' files
  called style.css cannot collide. Templates reach every file through
  {% static %}, never a hard-coded /static/ path, so STATIC_URL or the
  storage backend can change without touching a template. The font is
  self-hosted so a page load makes no third-party request, which suits an
  app whose premise is student privacy.

--------------------------------------------------------------------------------
S3 - Cache busting (explained, and implemented for the bonus)
--------------------------------------------------------------------------------
  The problem: browsers cache quadconnect.css. Cache it for a long time and
  returning visitors keep the OLD stylesheet after we deploy a change. Cache
  it briefly and every page view re-checks the file. Cache busting removes
  the trade-off by changing a file's URL whenever its content changes: an
  old URL can then be cached forever, because it will never mean anything
  else.

  How it is implemented (quadconnect/settings/production.py):
      STORAGES["staticfiles"] =
          "whitenoise.storage.CompressedManifestStaticFilesStorage"
    - python manage.py collectstatic --noinput copies every file into
      staticfiles/ a second time under a name with a hash of its content,
      plus staticfiles.json mapping each name to its hashed name.
    - {% static 'css/quadconnect.css' %} looks the name up in that manifest
      and prints /static/css/quadconnect.9d7082daf6a5.css (the build in
      screenshots 08 and 09).
    - url() references inside the CSS are rewritten too: the font becomes
      fonts/inter-latin-wght-normal.260c81a4759b.woff2.
    - WhiteNoise serves hashed files with
          Cache-Control: max-age=315360000, public, immutable
      and a gzip copy (4.8 KB instead of 16 KB). The unhashed name gets
      only max-age=60.
  Changing one character of the CSS changes its hash, so the next page
  links a new URL and every browser fetches it at once.
  Development keeps Django's default storage, so no collectstatic is needed
  while editing. Deploy step: collectstatic --noinput. staticfiles/ is
  gitignored.

--------------------------------------------------------------------------------
S4 - Memory when generating charts
--------------------------------------------------------------------------------
  - matplotlib.figure.Figure, never pyplot. pyplot keeps every figure in a
    global registry until plt.close(), so a view that forgets to close one
    leaks a figure per request. A bare Figure is freed when the view
    returns. pyplot's default backend on this machine is also TkAgg, a GUI
    backend that must not run inside a web server.
  - The PNG is written into an in-memory BytesIO buffer and sent with
    HttpResponse(content_type="image/png"). Nothing touches the disk and
    there are no temp files to clean up.
  - Fixed figsize (8 x 4.5 in) and dpi (150) cap each render at 1200 x 675
    px. The RGBA canvas is about 3 MB; the measured peak for a whole render
    was about 9 MiB, and the PNG sent is 48-66 KB.
  - Measured: 120 renders in one process retained about 240 KiB in total
    (Matplotlib's bounded text-layout caches), and no pyplot figures were
    left open. A leaked figure would cost megabytes per render.

--------------------------------------------------------------------------------
S5 - Adapting a class-based view to GET and POST
--------------------------------------------------------------------------------
  CampusLocationListView is a base View, so adapting it meant adding post()
  next to get(); both call one _render() so the list, filters and empty
  states are identical either way.
    GET   ?setting= and ?seats= filter the list. Nothing changes on the
          server, so the filters belong in a shareable URL.
    POST  "Suggest a venue" creates a row, so it must never happen on a GET
          (a link, a prefetch, a crawler). Valid: save unapproved, add a
          message, redirect (Post/Redirect/Get, so a reload cannot submit it
          twice). Invalid: re-render with an error summary and each error
          next to its field.
  The ModelForm's fields list is a whitelist that leaves out is_approved, so
  even a hand-crafted POST with is_approved=on cannot approve itself (there
  is a test for exactly that).

--------------------------------------------------------------------------------
S6 - How we plan to create the API, and what data it will serve
--------------------------------------------------------------------------------
  How (now): Django's own JsonResponse, no framework. A class-based View for
  the resource-style list (LocationListAPI, which can gain a detail or a
  post() later), a function-based view for a single-purpose query
  (match_list_api). Query parameters are validated with forms.Form classes;
  a bad value gets a 400 JSON body naming the parameter and how to fix it,
  never a silent fallback. Every list has the same shape: count, filters,
  results. /api/locations.txt is the same data through plain HttpResponse
  with text/plain, to show the MIME difference: JsonResponse serialises a
  dict and sends application/json, HttpResponse sends a string as whatever
  content_type says (text/html by default).
  Observed in the browser: Chrome shows its "Pretty-print" toggle only for
  the application/json responses; the text/plain one is shown as bare
  text (screenshots 15 and 18). A client calling response.json() on the
  .txt endpoint gets a parse error, because it is not JSON.

  What (now): public-by-design data only.
    - approved venues: name, address, arrival note, indoor/outdoor, seats,
      matches hosted, page URL
    - the match schedule: type, status, week, local time with UTC offset,
      venue, suggested activity, participant COUNT, page URL
  Never: student names, NetIDs, emails, check-in codes, feedback, private
  notes, unapproved venue suggestions. A test checks the payloads.

  Planned next:
    1. Version the prefix (/api/v1/) before any outside client depends on it.
    2. Authenticated endpoints for the signed-in student only:
         GET  /api/v1/me/match/                this week's match, including
                                               their own check-in code
         POST /api/v1/matches/<pk>/check-in/   Screen 8
         POST /api/v1/matches/<pk>/feedback/   Screen 9
       These change data, so they need login plus CSRF or token auth. At that
       point we would move to Django REST Framework for serializers,
       permissions and throttling rather than hand-roll them.
    3. Pagination (?page=) once lists outgrow one response.
  First consumers we have in mind: the campus map on Screen 8, which needs
  venues, and a phone-sized schedule view.

HttpResponse vs render()
------------------------
  [Dhruv]      The manual path made the request/response cycle visible.
               render() is really three steps welded together: load the
               template, render it against a RequestContext, wrap the string
               in an HttpResponse. Doing it by hand, I had to remember to pass
               `request` into .render() - and if you forget, the page still
               renders, it just silently loses the context processors. That is
               a nasty failure mode render() cannot have.
               What it cost: three extra lines and one real outage. Because
               the template is named in a string rather than by a shortcut,
               a typo in the filename is not caught until the view is actually
               requested - mine shipped with a trailing semicolon in the
               filename and returned a 500 until it was caught in review.
               render() would have failed identically, but the lesson stands:
               with the manual path there is nothing between you and the
               filesystem, so LOAD THE PAGE before you call it done.
               I would choose the manual path when the response is not a
               plain 200 HTML page - a custom status code, a non-HTML content
               type, or a streamed response.
  [Manojkumar] render() collapses three steps into one: it builds a
               RequestContext, loads the template, renders it, and wraps the
               result in an HttpResponse. Dhruv's view does the same work in
               four explicit lines. In practice the shortcut mattered less
               for the typing it saved than for what it prevents forgetting -
               with loader.get_template() you must remember to pass `request`
               into .render(), and if you skip it the page still renders but
               the context processors silently do not run. render() cannot be
               got wrong that way. I would reach for the manual path only
               when the response is not a plain 200 HTML page: a custom
               status code, a non-HTML content type, or a streamed response.

Base CBV vs Generic CBV
-----------------------
  [Prathamesh] Writing the base View made visible everything ListView does
               silently. In get() I had to build the queryset myself, apply
               each filter by hand, name the context keys, choose the template
               path, and shape every row - four jobs ListView infers from a
               single `model =` attribute. It is more code for the same page.
               What I gained was control: the filters interact (setting plus
               seats), the empty-state message changes depending on WHICH
               filter emptied the list, and the rows are pre-shaped so a
               model-agnostic template can render them. ListView would have
               fought me on all three. My rule now: generic view when the page
               is a plain list of one model; base View when the response
               depends on more than the model.
  [Kritika]    ListView gave me four things without my writing them: the
               queryset from a single `model =` line, the context name,
               pagination, and the template path by naming convention. Set
               model and context_object_name and the page exists. Prathamesh
               wrote all four by hand in get() for the same shape of page.
               Where it got in the way: the ?college= filter has to go in
               get_queryset(), and anything the TEMPLATE needs but the
               queryset does not carry - the current filter value, the list
               of colleges, the unfiltered total - has to go in a separate
               get_context_data(). One feature, two overridden methods, and
               you must remember to call super() in both. A plain function
               would have built one dict in one place.
               The real trap: I annotated the queryset with a Count, which
               adds a GROUP BY, and Django then DROPS Meta.ordering from a
               grouped query. Pagination silently became non-deterministic -
               a student could appear on two pages or none - and it only
               surfaced as an UnorderedObjectListWarning, not an error. Fixed
               with an explicit .order_by() after the annotate.
               My rule: generic view when the page is a plain list of one
               model; the moment the template needs context the model does
               not have, the saving starts to disappear.

Team-level observation
----------------------
  Having built all four over the same data, we would default to the generic
  CBV for anything that is genuinely "a list of one model" or "one row of one
  model" - it is the least code and the behaviour is predictable. We would
  reach for a plain function with render() the moment a page needs context
  the model does not carry, because one function building one dict is easier
  to read than two overridden methods calling super().
  The base View earns its place rarely: only when the response depends on
  something other than the model, and the generic machinery would be fought
  rather than used. The manual HttpResponse path we would keep for responses
  that are not plain HTML pages - a custom status code, a file download, a
  streamed response.
  The wider lesson from integration was not about views at all. Three of the
  four branches had a defect that no static check could catch - an unstyled
  CSS class, a filename typo that 500'd, an ordering bug that only warned.
  All three needed someone to open the page. manage.py check passing is not
  evidence that a page works.

7. CHALLENGES & OPEN QUESTIONS
================================================================================

- BASE_DIR had to change from parent.parent to parent.parent.parent when
  settings became a package. It fails silently if you miss it: Django looks
  for db.sqlite3 one directory too deep and creates an empty one. Worth
  knowing if anyone restructures again.
- RESOLVED in P1-A3: with DEBUG=False, runserver will not serve /static/, so
  A2 kept its CSS inline. P1-A3 moved the CSS to static/ and added
  WhiteNoise in the same change, so production still renders. It now needs
  collectstatic before it starts.
- UniqueConstraint cannot span relations, so "one match per student per week"
  is NOT enforceable in the model layer. It has to live in the matching
  service when we build it. Carried over from P1-A1.
- Venue suggestions (P1-A3 Section 5) are anonymous and not rate-limited.
  They are never published before review, but nothing stops a flood of
  unapproved rows. Require login (and throttle) before real students use
  it.
- Still unspecified: the matching algorithm itself. compatibility_score and
  match_reason exist as fields but nothing computes them outside seed data.
  This is the biggest open design question for the next assignment.
